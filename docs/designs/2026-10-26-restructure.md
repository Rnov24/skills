# Spec: Restructure the rnov24/skills entry layer (v1.18.0)

- Upstream: grill (interrogator) 2026-10-26, hypothesis anchored 19:45 WIB · Rubric (9 criteria) accepted 21:19 WIB · No brief, PRD, or stories exist for this change; the grill transcript and the rubric are the upstream. The hypothesis and the rubric are quoted in full in the Problem section below, so this document stands alone.
- Review history: Goldfish 5 stages 2026-10-26 ~21:42–21:52 WIB → NOT READY (2 Critical); triage (REVIEW.md, 0 contests) → v2; single permitted re-audit → READY AFTER FIXES (4 Required, 3 Nit); owner re-decided OQ1 to the clean rename 22:01 WIB → v3, with the re-audit's remaining fixes applied and the alias groups mooted by the rename.

## Problem and goal

The anchored hypothesis, in the owner's words as recorded in the grill: the suite's structure is hard to digest because its entry points do not follow the user's task verbs. "Improve UI" has no command; the 9 v1.17.0 commands cover only internal states of 4 skills (review, grill, recon, verify); everyday task verbs have no entry; the router `/rnov` does not read as "start here"; and the from-scratch vs improvement flows are invisible. The owner could not localise the confusion ("nah itu gatau bingung") — it is total, not one bad name. The concrete moment: wanting to improve a UI and not knowing which command to call.

The rubric this design is graded against (accepted 21:19 WIB, referred to below as R1–R9):

- R1. Improve UI and other everyday task verbs have one obvious entry point; no guessing.
- R2. From-scratch and improvement are two visible entry paths, not hidden in docs.
- R3. Every command maps to something the user would say, not to an internal skill state.
- R4. One read of the entry point lets a new user or agent state the suite's shape and what runs first.
- R5. Skills stay hardened as the count grows: validation that catches drift also applies to the new structure.
- R6. Gluttony absorption is lighter: the user can declare a source safe and skip the proving run.
- R7. Non-dev skills enter only on a concrete need (branding, video demo as examples).
- R8. Flows do not assume a web project; usable beyond web development.
- R9. Improve UI runs a combined impeccable + hallmark audit before any change.

Resolved fact, not an open question: "Hallmark" is not an outside repo. It is one of the five sources already synthesised into the `design` skill (Atelier, Impeccable, Hallmark, VoltAgent, Anthropic frontend-design); its contribution is the "slop test" sweep in `skills/design/references/taste-core.md` (the "Pre-ship slop gates" section). "Impeccable" is the frontend design skill whose mechanisms also live in `design`. So R9 means surfacing and combining audit machinery already inside `design` as the improve-UI entry, not absorbing anything new.

Goal: rebuild the suite's entry layer — the commands, the router, and the one page that explains them — so that every everyday task has one obvious entry point named in the user's own words, the two paths (from scratch, improvement) are visible on the surface, and improve-UI enters through the combined audit first. The skills themselves do not change except for the narrow additions this spec names (`design` gains an audit section; `gluttony` and `adapt` gain the lighter absorption rules). No new skill is created. The skill count stays 24.

## Solution outline

The entry layer becomes two kinds of command with different admission tests, both declared in the same manifest. A **verb command** names a task the user would say and the flow it runs: `/rnov-start` (front door), `/rnov-new` (from scratch), `/rnov-improve` (improve what exists), `/rnov-improve-ui` (improve a UI surface, audit first), `/rnov-fix` (fix a bug). A **state command** names a standalone audit or mapping unit the user invokes by name: `/rnov-goldfish` (full Goldfish protocol), `/rnov-bootstrap` (document an undocumented codebase), `/rnov-drift` (drift sweep). That is 8 manifest commands, down from 9. `/gluttony` is unchanged (slash-only skill, pre-dates this layer).

Five v1.17.0 commands are removed because they fail the "user would say it" test (R3): the three single Goldfish stages (`comprehension`, `critic`, `readiness`), `/rnov-lens-swarm`, and `/rnov-blind-doubt`. They are orchestrator-internal — the agent picks a stage or a lens swarm from inside the owning skill, and their gates belong to that skill (the lens swarm's readiness gate, the blind-doubt stakes rule), not to a slash shortcut. Their sections stay in the skills; only the user-facing command goes away. `/rnov` is renamed `/rnov-start` because the hypothesis names it: it does not read as "start here".

The manifest (`commands/commands.json`) gains two fields and the generator (`scripts/generate_commands.py`) gains four checks plus a second output. Every entry carries `kind` (`verb` or `state`); every verb entry except the front door (`rnov-start`, which classifies instead of running a fixed flow) carries `flow`, the ordered list of skills its flow runs. `flow` lists skills only; non-skill steps live in the command's steps. The generator validates that every skill in every `flow` exists, and fails generation if the manifest holds more than 12 commands — a mechanical backstop against the count growing back toward 31, since the v1.17.0 rule alone already produced commands the user never says. The generator also renders a second file, `docs/ENTRY.md`: the one-page entry map (front door, the two paths with their flows, improve a UI surface with its audit-first flow, fix, the three audit commands, and one paragraph stating the suite's shape and what runs first). The same map is rendered into the `/rnov-start` command file's Steps, so the agent reads it from the command that invoked it when installed; `docs/ENTRY.md` is the same map as a standalone page for humans. The installer (`scripts/install.py`) gains one behaviour: when installing commands to Claude Code it removes installed command files that the manifest no longer lists (renames and removals must actually leave the installed targets); the agy plugin needs no change because reinstall replaces the plugin wholesale.

The router skill (`using-rnov-skills`) is rewritten around the entry layer: its first lookup step becomes "Entry first — read the entry map (from the front-door command's Steps when invoked by one, or from `docs/ENTRY.md` in the repo)", its Standard flows become the verb commands' flows, and its Classify step gains a Domain question so the flows stop assuming a web project (R8). The `design` skill gains one new section, `## Audit an existing UI`, which sequences machinery that already exists (pre-flight scan, deterministic checks, the six-axis council review, the taste-core slop sweep) into a single named audit whose findings land in REVIEW.md; `/rnov-improve-ui` points at it (R9). Gluttony gains a declared-safe intake: when the human declares a source safe in writing, the EXPOSED → ADAPTED promotion no longer requires a proving run — the audit and verdicts still run, because the declaration covers safety, not quality (R6). Gluttony and `adapt` gain a need check: any brand-new skill (ABSORB-NEW) must record the concrete need it serves, or it is rejected (R7).

## Detail

### Terms used in this document

- **Entry layer.** The commands, the router skill, and `docs/ENTRY.md` — everything a user or agent reads before doing work. The skills are the knowledge; the entry layer is the address.
- **Verb command.** A command whose name is a task the user would say ("improve UI", "fix this bug", "start something new") and whose steps run a whole flow. A verb command's manifest entry carries a `flow`, the ordered skills the flow runs — except the front door, which classifies instead of running a fixed flow, and therefore carries no `flow`.
- **State command.** A command whose name is a standalone audit or mapping unit the user invokes by name ("goldfish this spec", "check for drift", "document this codebase"). A state command's manifest entry has no `flow`; it points at one section of one skill.
- **Front door.** `/rnov-start`: the one command for "I don't know where to start". It runs the router, and it classifies instead of running a fixed flow.
- **Flow.** An ordered skill chain from the router's Standard flows, e.g. new-product: setup → brief → research → grill → define-product → design → model → spec → tickets → implement → review → verify → ship → retro. A `flow` lists skills only; steps that are not skills (the audit, design deltas, the keyframe gate) live in the command's steps, never in `flow`.
- **Capability skill.** A skill that is a standalone capability rather than a pipeline phase (for example `f1-predict`, `data-viz`, `mcp-builder`, `study`). Capability skills are invoked by name in prose; they get no command, because their names already are the verbs.
- **Declared-safe.** A written statement by the human, recorded in the absorb report, that an absorption source is a repository the human knows and trusts. It declares safety only.
- **Concrete need.** A named project, deliverable, or recurring task that will use a proposed new skill, stated in one sentence in the absorb report or the skill proposal. "Might be useful someday" is not a concrete need.

### The command set (R1, R2, R3)

The manifest after this change holds 8 commands. Each entry is justified by a named flow difference, not by symmetry.

| Command | Kind | What the user says | Flow / section |
|---|---|---|---|
| `/rnov-start` | verb | "Start here / I don't know where to start" | router (`using-rnov-skills`), whole skill |
| `/rnov-new` | verb | "Start something new" | setup → brief → research → grill → define-product → design → model → spec → tickets → implement → review → verify → ship → retro |
| `/rnov-improve` | verb | "Improve this" | brief (short) → grill (new decisions only) → define-product (delta stories) → design/model deltas → spec → tickets → implement → review → verify → ship |
| `/rnov-improve-ui` | verb | "Improve this UI" | audit (`design`, Audit an existing UI) → design deltas → keyframe gate → implement → review → verify |
| `/rnov-fix` | verb | "Fix this bug" | debug → implement (one ticket) → review → verify |
| `/rnov-goldfish` | state | "Goldfish this spec" | `review`, Goldfish protocol (all five stages) |
| `/rnov-bootstrap` | state | "Document this codebase" | `recon`, Bootstrap mode |
| `/rnov-drift` | state | "Has the code drifted from the docs?" | `verify`, Drift sweep |

The table shows the user-facing sequence; the manifest `flow` field holds the skills-only chain (`design → implement → review → verify` for improve-ui) and the non-skill steps live in the command's steps.

Why these five verbs and no more. `/rnov-new` and `/rnov-improve` are R2 made visible: the two paths must exist as distinct commands, because a single front door would hide the from-scratch/improvement split inside the router's head — the exact invisibility the hypothesis names. `/rnov-fix` earns its place by flow divergence: the bug flow skips brief, grill, and spec entirely, so routing a bug through `/rnov-improve` would load the wrong machinery (a PRD delta for a one-line fix). `/rnov-improve-ui` earns its place the same way: its entry is the audit, not the brief. A question ("ask") gets no command: the user asks questions in prose and the model already routes prose to `research`; a command would add a name without adding a flow. Capability skills (`f1-predict`, `data-viz`, `mcp-builder`, `study`, `research`) get no command: their names are already the entry point in prose, and one command per capability is the count growth the owner rejected.

Removed commands, and why each one goes. `/rnov-goldfish-comprehension`, `/rnov-goldfish-critic`, `/rnov-goldfish-readiness`: the protocol's value is the sequence (comprehension → critic → readiness, framed by two zoom-outs); a single stage is picked by the orchestrator mid-review, never by the user. The full-protocol command covers the user case. `/rnov-lens-swarm`: the swarm's own readiness gate (hypothesis anchored, human confirms readiness) belongs to the `grill` skill; a slash shortcut invites unanchored swarms, and "swarm" is not user language. `/rnov-blind-doubt`: the review skill runs blind doubt by stakes, "not performed ritually every time"; a command invites ritual use. In all five cases the skill section stays, the router still dispatches to it, and only the user-facing command is removed. The commands are two hours old (v1.17.0 released 2026-10-26 ~19:19 WIB) and the owner is the only user, so the migration cost is one line in the release notes.

The rename `/rnov` → `/rnov-start` is the direct fix for the hypothesis's named defect. No alias is kept: two names for one door is the same confusion in miniature, and the manifest has no alias concept. The old name dies in v1.18.0.

The command-count cap is 12. The manifest holds 8 after this change, leaving headroom for 4 future entries. Raising the cap is a human decision recorded in `docs/COMMANDS.md`; the generator refuses to run above it. The cap is a guardrail, not a target.

### The entry map (R4)

`docs/ENTRY.md` is the one page a new user or agent reads. It is generated from the manifest by `scripts/generate_commands.py`, so its command list and flow chains cannot drift from the manifest; it is never edited by hand. Its contents, in order: the front door (`/rnov-start`, what it does, what to type); the two paths (`/rnov-new` and `/rnov-improve`, each with its flow chain spelled out); improve a UI surface (`/rnov-improve-ui`, audit first, with its flow); fix (`/rnov-fix`, its flow); the three audit commands with their one-line purposes; and a "Shape of the suite" paragraph. That paragraph is rendered from the manifest (the two paths, the fix flow, the audits) plus one fixed sentence for the router rule, and its exact text is: "The suite is one pipeline entered through two paths: `/rnov-new` starts something new and `/rnov-improve` improves what exists. `/rnov-fix` joins the pipeline at implement, skipping setup through tickets. Audits run before changes. Whenever a task matches no command, `/rnov-start` decides." The drift guarantee covers the derived parts; the fixed sentence is re-read at the release gate. The test for R4 is a human one, stated in Test seams: a new reader reads ENTRY.md and states the shape and what runs first; if they cannot, the map fails, not the reader.

The human entry point is the README: it gains a "Start here" section at the top listing the five verb commands and pointing at `docs/ENTRY.md`. The ASCII pipeline diagram stays — it is the phase map, not the entry map. The agent entry point is `/rnov-start`: its generated steps carry the entry map itself, then classify.

### The router rewrite (R1, R2, R4, R8)

`skills/using-rnov-skills/SKILL.md` changes in three places. First, the lookup protocol's step 1 ("Commands first") becomes "Entry first": read the entry map — from the front-door command's Steps when invoked by one, or from `docs/ENTRY.md` in the repo; if the task matches a verb command, the command names the flow — load the command file, not the skill; if it matches a state command, the same; only if nothing matches does the router classify from scratch. The rewrite drops the old step-1 examples (`/rnov-goldfish-critic`, `/rnov-lens-swarm`), which name commands this change removes. Second, the "Standard flows" list is rewritten so each flow line is the verb command's flow, with the command name on the line (the manifest anchors point at these lines; see Detailed Implementation for the exact anchor strings the implementer must preserve). Third, the Classify step gains a fifth question, Domain: what kind of thing is this — software, analysis, media, document, or something else? The answer decides which phases apply and which are skipped with a recorded reason (see "Beyond web" below). The disambiguation pairs, the phase check, the regenerate-on-drift step, and the no-match rule are unchanged.

### The design audit section (R9)

`skills/design/SKILL.md` gains one new section, `## Audit an existing UI`, placed after "Working on an existing project" and before "Build discipline". It is a sequencer, not new rules: it names the order in which existing machinery runs, and nothing else. The sequence is: (1) the pre-flight scan, as defined in "Working on an existing project" (scan DESIGN.md, font stack, palette tokens, motion libraries, spacing scale, framework; file:line citations; cache in `.work/design-preflight.json`); (2) the deterministic checks from `references/review-rubric.md` (screenshots at smallest and largest supported widths, measured contrast, no overflow, touch targets, token tracing, all states captured, click-through, keyboard walk, reduced-motion pass, layout-shift observation, placeholder scan, stamp-lies check, DESIGN.md drift check) — these run before any axis discussion, because a screen that fails measurement does not earn a taste discussion; (3) the six-axis council review from `references/review-rubric.md` (product fit, typography and layout, colour and tokens, interaction and states, accessibility, craft and anti-slop), lenses in parallel, dissent recorded, two rounds maximum; (4) the slop sweep from `references/taste-core.md` ("Pre-ship slop gates": motion mechanics, colour mechanics, layout safety, structure and chrome, type and token discipline), which is the Hallmark slop test as synthesised into this suite; (5) findings written to REVIEW.md under an "Audit" heading, each with a severity from the suite's scale (Critical, Required, Nit, Optional, FYI, as defined in the `review` skill, "Two axes, never merged"), no AC verdicts (no acceptance criteria exist yet for a pre-change audit); (6) a verdict line stating what changes and what does not, and whether the improvement proceeds. No change is made before the audit lands in REVIEW.md. The section must contain the sentence "Audit findings land in REVIEW.md under an Audit heading, with severities from the suite's scale." — that sentence is the generator anchor for `/rnov-improve-ui`. When the change is a single element, the audit runs in component scope as defined in "Working on an existing project" (page machinery stands down; the deterministic checks and the council scope to the component; the slop sweep still runs).

The audit's council is the design skill's existing council review (distinct lenses, dissent recorded, two rounds), not a second council. The audit does not re-run the preview block or the diversification log: those belong to new-direction work, and an audit judges what exists. After the audit, the improvement proceeds through the existing mechanics: design deltas (amend DESIGN.md; a Variants entry first if breaking the locked system, per "Redesign inversion"), the keyframe gate for visible changes, then implement → review → verify. The audit's Critical findings must be closed or ruled on before ship; the ruling names who ruled and why, per the suite's existing convention for accepted trade-offs.

### Gluttony, lighter (R6, R7)

Two changes to `skills/gluttony/SKILL.md`, both in the intake and staging, neither touching the audit. First, the declared-safe intake. Section 1 (Intake) gains the rule: when the human declares a source safe — in the run's opening message, in words ("I know this repo, it's safe") — the run records the declaration in the absorb report (who declared, the exact words, when). The declaration is the recording rule for the existing written-ruling promotion path: a ruling promotes only when it records the safe-declaration or cites a proving run. The audit (section 3), the verdicts (section 4), and the adaptation rewrite (section 5) still run in full: the declaration covers safety, not quality, and a declared-safe repo full of filler still earns REJECTs. The vet-before-trusting step stays: every script, hook, and installer is read before anything runs, and the declaration never authorises executing upstream code. Second, the need check. Section 4 gains the rule: any ABSORB-NEW verdict must record the concrete need it serves (one sentence: the project, deliverable, or recurring task that will use it). A unit with no named need gets REJECT with the reason "no concrete need named". The worked examples in the skill are branding and video demo as passing needs, and "might be useful someday" as the failing case.

`skills/adapt/SKILL.md` mirrors both changes. Its staging section's written-ruling path is amended the same way (it requires the safe-declaration record). Its candidate section gains the need check for owner-proposed new skills (not only gluttony imports): a proposal must name its concrete need before it becomes a candidate. `templates/absorb-report.md` gains `Need:` as a column in the Audit and verdicts table and `Safe declaration:` as a header field, so the checks are recorded in the artifact rather than in chat. The proving-run machinery itself (`adapt`, "Proving runs for design mechanisms": brief-to-output pairs) gains the exception sentence ("except where a declared-safe source is recorded under staging") and still applies to design mechanisms and to any absorption the human did not declare safe.

### Hardening (R5)

The generator (`scripts/generate_commands.py`) gains four validations and one output. It validates that every manifest entry has `kind` in {`verb`, `state`}; that every verb entry except the front door (`rnov-start`, which classifies instead of running a fixed flow) has a non-empty `flow` whose every skill exists under `skills/`; that every manifest `flow` equals the arrow-chain on its router line (matched by anchor), compared by skill tokens with annotations such as `(if absent)` stripped; and that the manifest holds at most 12 commands, failing with the message "command cap exceeded (N > 12); raising the cap is a human decision recorded in docs/COMMANDS.md". It renders `docs/ENTRY.md` from the manifest alongside the command files, and renders the same map into the `/rnov-start` command file's Steps by expanding the `{{ENTRY_MAP}}` token in its `steps` list; `--check` verifies ENTRY.md and the front-door file match what would be generated, exactly as it verifies the command files. The existing verifications are unchanged (section exists, anchor sits inside the section, no duplicate names, one token per name, description/argument-hint/output/steps non-empty).

The installer (`scripts/install.py`) gains stale-cleanup in `install_commands`: after installing the manifest's commands to `~/.claude/commands/`, it removes any `.md` file there that is recorded in the install manifest's `commands` section but is no longer in `commands/commands.json`. Only files the installer itself installed are removed, per the existing safety model; a foreign file in that directory is left alone and reported by name. On a dry run it reports what it would remove and removes nothing; `--check` asserts that no stale command files remain installed. The agy plugin path needs no change: reinstall replaces the plugin wholesale, and `agy plugin validate` runs on the staged plugin before install, as today. The Codex path needs no change: it installs skills only, and no skill is added, removed, or renamed by this change.

What the validation layer cannot do is stated plainly, not hidden: the "user would say it" test (R3) and the "concrete need" test (R7) are human judgments recorded in artifacts (the manifest's descriptions, the absorb report's `Need:` field). No script judges them. Their enforcement is the human gate: the review gate for absorptions, and the release gate for command changes.

### Beyond web (R8)

`docs/WORKFLOW.md` gains a short "Beyond web" paragraph at the top, after the Principles: the pipeline is a decision-and-evidence pipeline, not a web pipeline. The entry layer is domain-neutral (the two paths, fix, and the audits name no technology). The phase skills are software-flavoured by history (`model` assumes an ERD and an API, `implement` assumes code); outside software, those phases are skipped with a recorded reason, per the router's existing skipping rule, and the gates that do not assume software — human approvals, review, verify — still apply. A worked example is named in the paragraph: a non-software deliverable (an analysis report, a video series) enters through `/rnov-new` or `/rnov-improve`, runs brief → grill → define → spec → tickets → review → verify → ship, and skips design, model, and implement-as-code with reasons recorded. The router's new Domain question is what makes the skip explicit at classification time instead of discovered mid-run. The honest limit, stated in the paragraph: this change makes the entry and the routing domain-neutral; it does not rewrite the phase skills for other domains. A phase skill that cannot serve a domain is skipped, not forced.

## Alternatives considered

- **One command per skill (31 commands, the pre-v1.17.0 design).** Rejected: the owner already rejected it as "kebanyakan", and skills are already invocable by name in prose, so a command per skill adds names without adding entries.
- **One front door only (`/rnov-start`, no verb commands).** Rejected: R2 requires two visible paths, and a single door hides the from-scratch/improvement split inside the router — the exact invisibility the hypothesis names. It also leaves "improve UI" with no entry of its own, so the audit-first requirement (R9) would have nowhere to attach.
- **Keep all 9 state commands and add the verbs (15 commands).** Rejected on two grounds: R3 (the five removed commands are not user language), and count drift (15 is halfway back to 31 with no principled stop). The five removed units stay reachable through their skills and the router.
- **Task verbs as new skills (for example a new `improve-ui` skill).** Rejected: the knowledge already lives in `design` (and `review`); a new skill duplicates it and grows the skill count, which is the bloat this restructure exists to stop. Commands are the thin layer; skills are the knowledge.
- **Aliases (keep `/rnov` and add `/rnov-start`).** Rejected: two names for one door is the same confusion in miniature, and the manifest has no alias concept — adding one is mechanism for a naming problem solved by renaming. The owner first chose the alias period (21:38 WIB), then re-decided to the clean rename (22:01 WIB) after the Goldfish review showed both names would sit side by side in Antigravity's slash picker. The rename costs one line in the release notes.
- **Hand-written `docs/ENTRY.md` and hand-written command files.** Rejected: drift. The generator plus `--check` is the suite's proven mechanism (v1.17.0's negative test: renaming a section fails generation naming the command). A hand-written map would be wrong within one release.
- **No command cap; rely on the "user would say it" rule alone.** Rejected: the v1.17.0 rule already produced commands the user never says. A rule that failed once needs a mechanical backstop; the cap is that backstop, set at 12 with headroom for 4.
- **Proving run stays mandatory for every absorption (no declared-safe path).** Rejected: the owner's explicit complaint is that the user knows whether a source is safe. The design splits the concern instead of dropping it: the audit (quality) stays mandatory, the proving run (promotion evidence) is waived only on a written safe-declaration.
- **Improve-UI as a new skill absorbing the impeccable and hallmark repos.** Rejected: both are already synthesised into `design` (see the resolved fact in the Problem section); absorbing them again duplicates the suite and violates the standing prejudice against a second taste manifesto. R9 is surfacing and sequencing, not absorbing.
- **Stale command files left in place on the installed targets (no installer cleanup).** Rejected: the rename and the five removals would then be repo-only changes, and the owner's Antigravity and Claude Code would keep offering commands that no longer exist. The cleanup is the part of the change the user actually feels.

## Test seams

Also, in a throwaway copy, add a 13th manifest entry and run the generator — it must fail with the cap message.

- Stale-cleanup seam: the installer test runs with `HOME` pointed at a scratch directory (install.py reads the home directory from the environment, so `HOME=/tmp/<scratch>` is enough) containing a fake `~/.claude/commands/` with the five removed command files and `rnov.md` present and recorded in a fake install manifest; after install, those six files are gone and the eight current ones exist. Foreign files in that directory (not in the install manifest) are left alone.

Release-gate check: read the installed `plugin.json` commands array (`~/.gemini/config/plugins/rnov-skills/plugin.json`) and compare it against the manifest; a stale served list fails the gate.

## Heilmeier

1. **What are you trying to do, in plain words?** Make the suite's entry points follow the user's task verbs, so that "improve UI" and every other everyday task has one obvious command to call, the two paths (from scratch, improvement) are visible on the surface, and improve-UI starts with a combined audit instead of a guess.
2. **How is it done today, and what are the limits?** v1.17.0 has 9 commands: a router that does not read as "start here" and 8 state commands covering internal sections of 4 skills. Everyday verbs have no entry; the user cannot say which command a task needs and cannot localise the confusion; the from-scratch vs improvement split is hidden in the router's prose.
3. **What is new in your approach, and why will it succeed?** Two command kinds with different admission tests (verb commands for flows, state commands for audits), decided by the owner's own words; a generated one-page entry map whose command list and flow chains cannot drift from the manifest; and a mechanical count cap, because the previous rule alone already produced commands the user never says. It will succeed because every entry is traceable to a sentence the owner actually said in the grill, and the count goes down (9 → 8) while the coverage of everyday verbs goes up.
4. **Who cares, and what difference will it make?** The owner, in Antigravity first: the next "improve UI" has one command to type instead of a guess. Future agents and users of the suite: one read of ENTRY.md tells them the shape and what runs first. The suite itself: the entry layer stops growing by accretion, because every future command must pass the verb test and the cap.
5. **What are the risks?** The rename breaks one release of muscle memory; a user who types `/rnov` gets nothing. The agy loader could serve a stale command list after reinstall — the release gate checks the installed plugin.json against the manifest. The five removals strand anyone who learned the single-stage Goldfish commands in the last few hours (only the owner). The audit section could become a second taste manifesto if an implementer adds rules instead of sequencing — the spec forbids it, and the review gate must check it. The stale-cleanup could delete a file the owner placed by hand — the safety model (only files the installer recorded) bounds it.
6. **How much will it cost?** One implementation pass: a manifest rewrite, a generator extension, a small installer behaviour, five skill edits, and doc updates — the file list in Detailed Implementation (31 files touched: 15 changed, 5 generated command files created, 6 generated command files deleted, 3 regenerated, 2 new docs). No new dependencies, no new tools, no new skills.
7. **How long will it take?** A single tickets pass after the Goldfish review: the manifest and generator first (the `design` section must exist before its command is generated), then the installer, then the docs, then the proving run as a follow-up ticket. The spec does not fix a calendar duration; the ticket graph does.
8. **What are the mid-term and final exams?** Mid-term: `generate_commands.py --check` and `install.py --check --all` pass on the new set, and the negative tests (renamed section, 13th command, stale files) all fail loudly as specified. Final: the rubric's nine criteria, graded by the owner — R1 by typing "improve UI" and four other verbs, R4 by the one-read check in Test seams, R9 by the improve-UI proving run.
